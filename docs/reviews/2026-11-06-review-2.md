## X1. [security, medium] On the Render deploy that render.yaml sets up, the rate-limit key is a Cloudflare edge address, so unrelated buyers and sellers share one bucket

`src/lib/http/client-ip.ts:5`

**Scenario:** clientIp() uses the rightmost X-Forwarded-For entry as the caller's address. Render web services sit behind Cloudflare, and a published write-up of Render requests shows the header as `X-Forwarded-For: <client>, <Cloudflare edge>` (example: `99.61.165.29, 104.22.17.40`). Render staff also say they put the real client first and append to the header. So on the deployed app the key for every route is the Cloudflare edge address, which is shared by everyone routed through the same Cloudflare location.

A throwaway Vitest confirmed the mechanism. Two different buyers' Render-style headers (`99.61.165.29, 104.22.17.40` and `203.0.113.9, 104.22.17.40`) both give the key `104.22.17.40`. After 20 allowed `assistant:` hits from the first buyer, the second buyer's first hit is refused.

What judges and buyers in the same region would hit:
(1) The buyer console allows 20 turns per hour (src/app/api/assistant/[slug]/route.ts:40-41). That becomes 20 per hour for everyone at that edge, and later visitors get 429 "You've sent a lot of messages".
(2) The console passes the same address as the buyer IP, so the door's per-caller unpaid-order cap (MAX_OPEN_ORDERS_PER_CLIENT = 3, keyed by `console:<edge>`) and the create_order limit of 30 per hour are shared. Three judges who start an assistant order on the demo shop without paying block create_order for every other judge at that edge with TOO_MANY_OPEN_ORDERS for up to 60 minutes. Outside MCP clients going through the same edge share the request-IP key in the same way.
(3) allowSetup allows 10 shops, 20 retakes and 20 live readings per hour per address. That becomes a regional quota: one anonymous attacker sends 10 cheap `POST /api/shops {"sample":"marigold-bakehouse"}` requests, and nobody else at that edge can start a shop for an hour ("You've started a lot of shops").

The Render header layout comes from third-party evidence, not from Render's own docs. Confirm it by logging the X-Forwarded-For, CF-Connecting-IP and True-Client-IP headers once on the deployed service.

**Skeptic's evidence:** I tried to refute this and could not. Severity drops from high to medium for the reasons at the end.

Code walk-through: src/lib/http/client-ip.ts:5 always returns `.at(-1)` of X-Forwarded-For. Every rate-limit key goes through it:
- src/app/api/assistant/[slug]/route.ts:40-41: `assistant:<ip>`, 20 per hour.
- src/lib/mcp/server.ts:37: doorRateIdentity(req, clientIp(req)). The console path becomes `console:<buyerIp>` (src/lib/agent/console-key.ts:23-31), which feeds the per-tool limits at src/lib/mcp/tools.ts:185 and clientKey at :283. clientKey is the MAX_OPEN_ORDERS_PER_CLIENT=3 check in src/lib/orders/service.ts:157-166.
- src/app/api/shops/route.ts:35 and src/app/api/shops/[id]/extract/route.ts:40,58: allowSetup (src/lib/rate-limit.ts:43-47, 10/20/20 per hour).
No guard elsewhere: no middleware or proxy file, and no other header is consulted.

Not already covered: R1-R13 and the Refuted section never discuss how the key is derived. DECISIONS.md has nothing on X-Forwarded-For or proxies. tests/http/client-ip.test.ts only pins the rightmost rule with a generic two-entry header.

Deployment premise (third-party, as the reviewer says):
- rohitpaulk.com 'render-rails-remote-ip' shows `X-Forwarded-For: 99.61.165.29, 104.22.17.40` on Render and says the second entry is a Cloudflare edge address. It reports that Render support recommends True-Client-IP / CF-Connecting-IP.
- In the feedback.render.com 'send-the-correct-xforwardedfor' thread, a Render staff member says the first IP is the real client, and a user notes that Render does not clear a passed-in X-Forwarded-For. Both fit `<client>, <edge>`, where the rightmost entry is the edge.
- render.yaml and README 'Deploy to Render' make Render the intended hosted-demo path. README:116 says the deploy has not been run yet, so the layout has never been seen on this service.

Throwaway test tests/zz-verify-security-1.test.ts (ran it, 4/4 passed, then deleted it):
(a) clientIp gives 104.22.17.40 for `99.61.165.29, 104.22.17.40`, for `203.0.113.9, 104.22.17.40` and for `1.1.1.1, 203.0.113.9, 104.22.17.40`.
(b) After 20 allowed `assistant:` hits from buyer A, buyer B's first hit is refused.
(c) Real POST /api/shops with SHELFIE_TEST unstubbed: 10 `{"sample":"marigold-bakehouse"}` requests from client 198.51.100.66 return 201, then a different client 203.0.113.9 at the same edge gets 429.
(d) A two-hop pick (`.at(-2)`) returns the real client even when a spoofed leftmost entry is present.

Why medium, not high: it only affects availability (429 / TOO_MANY_OPEN_ORDERS). Money, data and auth are not at risk. It depends on a deploy that has not happened yet and on a header layout known only from third-party reports. Cloudflare reaches the origin from a pool of addresses per location, so a bucket is shared by a group of visitors, not by literally everyone in a region. It is still a real, judge-facing failure on the intended hosted demo: 20 console turns per hour, 3 unpaid console orders, and 10 shop starts per hour, all shared across unrelated visitors.

**Fix:** Smallest safe change, in src/lib/http/client-ip.ts only.

When `process.env.RENDER` is set (Render sets RENDER=true on every service), return the trimmed `cf-connecting-ip` header first if it is non-empty. Cloudflare overwrites that header on every request. Otherwise keep today's rule: the rightmost X-Forwarded-For entry, then X-Real-IP, then 'local'. Never read cf-connecting-ip when RENDER is unset, because locally a client can send it to dodge the limits.

Add unit tests in tests/http/client-ip.test.ts (stub RENDER=true):
- `cf-connecting-ip: 203.0.113.9` with `x-forwarded-for: 6.6.6.6, 203.0.113.9, 104.22.17.40` gives 203.0.113.9.
- Without RENDER, the same headers give 104.22.17.40 (unchanged).

Prefer this over a TRUSTED_PROXY_HOPS=2 default in render.yaml. If the deployed header ever has only one proxy hop, `.at(-2)` returns a client-supplied entry, and anyone could bypass every limit by rotating a spoofed X-Forwarded-For. After the first deploy, log X-Forwarded-For, CF-Connecting-IP and True-Client-IP once to confirm the layout.

**Status:** fixed (`906a26a`): on Render (`RENDER` set) the rate-limit key is `CF-Connecting-IP`; elsewhere the rightmost `X-Forwarded-For` rule is unchanged. Unit-tested; **not verified on a real Render deploy** (the app has never been deployed).

## S1. [setup, medium] A tiny, high-resolution photo makes anyone's upload use hundreds of MB of memory and tens of seconds of CPU (image decompression bomb)

`src/lib/uploads.ts:50`

**Scenario:** normalizePhoto calls sharp(input) with sharp's default limitInputPixels, which is 268 MP, and four photos are normalised in parallel (Promise.all in createShopFromPhotos and setShopPhotos). An anonymous POST /api/shops with 4 copies of a 16000x16000 solid-colour PNG passes every check: each file is 0.78 MB, far under the 15 MB cap and the Content-Length check, and its format is png. I measured this with a throwaway vitest that called the real normalizePhoto (since deleted). 4 photos in parallel took 6.7 s and RSS grew by 312 MB. 8 photos in parallel (two such requests) took 27 s, and peak RSS went from a 90 MB baseline to 596 MB. render.yaml deploys on a 512 MB plan, so two requests from one address, well inside the 10 shops/hour limit, or the retake route (20/hour), can OOM-kill the single Node process. That takes down every shop page, the agent door and the payment poller. The rate limit does not help, because each request costs this much on its own.

**Skeptic's evidence:** src/lib/uploads.ts:50-56 calls sharp(input).metadata() and then sharp(input).rotate().resize(...) with sharp's default limitInputPixels (about 268 MP). The only size guard is the byte cap (MAX_PHOTO_BYTES 15 MB, line 48). Callers decode in parallel: createShopFromPhotos (src/lib/catalog/setup.ts:49) and setShopPhotos (setup.ts:69) both use Promise.all(photos.map(normalizePhoto)). POST /api/shops is anonymous; its allowSetup limit of 10 per hour does not help, because one request is enough. I ran a throwaway vitest (tests/zz-verify-setup-2.test.ts, now deleted) that called the real normalizePhoto. A 16000x16000 PNG is 776,180 bytes, and four of them in parallel all succeeded in 3.5 s, with RSS going from 89 MB to a 523 MB peak (+434 MB). render.yaml deploys on plan 0.5c-512mb, so one anonymous request can OOM-kill the single Node process, which also runs the agent door and the payment poller. A pixel cap alone is not enough. Four 8000x6000 (48 MP) PNGs in parallel still added 236 MB, so the parallel decode has to go too. The earlier review's R11 and R13 covered rate limits and JSON body size, not decoded pixel size. DECISIONS.md has no entry on this.

**Fix:** In normalizePhoto, after metadata(), throw UploadError('PHOTO_TOO_LARGE') when meta.width * meta.height exceeds a cap of about 50 MP (a 50 MP phone JPEG is still within the 15 MB byte cap and decodes cheaply through shrink-on-load). Pass the same cap as { limitInputPixels } to both sharp() calls. In createShopFromPhotos and setShopPhotos, replace Promise.all(photos.map(normalizePhoto)) with a sequential for...of loop. Optionally add a module-level one-slot queue so concurrent requests can't stack decodes. Add a unit test where a large-dimension, small-byte PNG (sharp create + png) is refused.

**Status:** fixed (`2a93b38`, `633d557`).

## S2. [setup, low] Prices from $500.01 to $1,000 (and $0) pass review and publish but the door can never sell them

`src/lib/ai/normalize.ts:103`

**Scenario:** Review and normalize accept item prices up to MAX_PRICE_CENTS = $1,000 (rules.ts:5, edits.ts:21, PriceInput's 'up to $1,000' hint). normalize only flags a price as unusual when it is <= $0 or > $1,000. But every shop is created with order_cap_cents DEFAULT 50000 ($500, schema.sql:14), which nothing in setup can change, and priceOrder throws ORDER_TOO_LARGE for any order over the cap (pricing.ts:178). Confirmed with a throwaway vitest: a bakery reading 'Wedding cake $650' (amount_cents 65000) produces an item with issues [] that goes straight to 'Ready for PayPal'. publishShop creates the PayPal product and marks it live, and priceOrder for 1 of it throws 'takes online orders up to $500.00'. The seller is told it is in PayPal and counted as live, list_products shows it with its price, and every buyer or agent order for it fails. A seller typing 600 into a ReadyRow price field gets the same result with no warning. Similarly, a $0 price is accepted (parsePriceInput('0') = 0, cents min(0)), is 'Ready', and is published to PayPal, but pricedOptions filters priceCents > 0, so the door answers 'The shop has not set a price for it yet.'

**Skeptic's evidence:** Throwaway vitest (tests/zz-verify-setup-1.test.ts, now deleted): normalizeExtraction on 'Wedding cake' with amount_cents 65000 gave issues []. publishShop gave {published:1, failed:[]} and left the shop and item live with orderCapCents 50000. priceOrder then threw 'This order comes to $650.00; B takes online orders up to $500.00.' The relevant code: isUnusual flags only <= 0 or > 100000 (src/lib/ai/normalize.ts:15, 103). The edit schema and parsePriceInput allow up to MAX_PRICE_CENTS = 100000 (src/lib/catalog/rules.ts:5, 48; edits.ts:21). The cap is order_cap_cents DEFAULT 50000 (src/lib/db/schema.sql:14), and no route edits it. Applied in src/lib/orders/pricing.ts:178. A $0 price can be accepted and published (cents min(0); parsePriceInput('0') = 0), but pricedOptions (pricing.ts:48-49) hides it. I downgraded it to low. The spec sets both numbers on purpose (CHECK above $1,000 at spec line 62, the $500 cap at lines 98 and 202). The door fails gracefully, with ORDER_TOO_LARGE and 'contact the shop directly'. The $0 path needs the seller to type 0 or click 'Looks right' on a CHECK card that already calls $0 unusual. No money is at risk. The cost is a listed item that can't be ordered online, and the seller isn't told.

**Fix:** Align the review limit with what the door can sell. Set rules.ts MAX_PRICE_CENTS to 50_000 (the default order cap). That one constant already drives parsePriceInput and the edits `cents` schema, and the PriceInput hint must change to match. Give variant prices a separate schema of z.number().int().min(1).max(MAX_PRICE_CENTS), keeping min(0) for shippingFeeCents. Make normalize's MAX_PRICE_CENTS import the same constant, so readings above $500 get a CHECK card. Add a test that every isPublishable item can be priced by priceOrder at quantity 1. Alternatively, raise the default order cap to $1,000 to match the spec's CHECK threshold.

**Status:** fixed (`bb9d94e`).

## S3. [setup, low] Publish overwrites edits saved while it runs: an item the seller removed during publish goes live and can be ordered

`src/lib/db/repos/items.ts:111`

**Scenario:** publishShop snapshots the items to publish at the start (publish.ts:160). After each createProduct, setPayPalProductId runs `UPDATE items SET paypal_product_id=?, status='live' ... WHERE id=?` with no condition on the current status. PATCH /items accepts status 'removed'/'in_person', renames and price changes for any item without a paypal_product_id, even while a publish run is in progress. Confirmed with a throwaway vitest: start publishShop with a deferred createProduct, apply {status:'removed'} to 'Old cake' (the DB shows 'removed'), release PayPal, and the item ends up status 'live' with a product id. The door then lists it and sells it. Several paths reach this in the UI. (1) ReviewStep.doPublish awaits autosave.flush() with no busy state and the review screen still editable, so a Remove or edit tapped during that network wait (seconds on a phone) is queued and sent at the same moment as POST /publish. (2) A connection drop mid-publish shows 'Back to review' while the server run carries on (by design), so the seller can remove or rename items it is still sending. (3) A second tab. Renames and price changes made the same way leave the PayPal product's name different from what the door sells, the opposite of the 'name and price are fixed once in PayPal' rule in checkLiveEdit.

**Skeptic's evidence:** publishShop takes its snapshot once (src/lib/catalog/publish.ts:160), then for each item calls createProduct(productFor(item)) with that stale copy and items.setPayPalProductId (src/lib/db/repos/items.ts:111-113), which runs an unconditional `SET paypal_product_id=?, status='live'`. checkLiveEdit (src/lib/catalog/edits.ts:84-92) only blocks items that already have a paypalProductId, so PATCH /items can set 'removed' on an item that is queued but not yet sent. A throwaway vitest (tests/zz-verify-setup-1.test.ts, now deleted) gated createProduct, applied {status:'removed'} through parseItemUpdates and applyItemUpdates, and logged 'S3 before removed'. After the gate was released it logged 'S3 after live PROD-FAKE00000004'. Reachable through the UI: after a dropped stream, usePublish shows 'Back to review' (ReviewStep.tsx:188-200), and the review is editable while the server run carries on at 3 items at a time, so items later in the queue can still be removed. doPublish (ReviewStep.tsx:143-147) also leaves the screen editable during `await autosave.flush()`. I downgraded it to low. Each path needs the seller to edit within a publish run of a few seconds, and the outcome can be undone: a live item can still be removed from the dashboard (checkLiveEdit allows status 'removed').

**Fix:** Make the write conditional in items.setPayPalProductId: `UPDATE items SET paypal_product_id = ?, published_at = ?, updated_at = ?, status = CASE WHEN status = 'draft' THEN 'live' ELSE status END WHERE id = ?`. A removed or in-person item then keeps its status, and the recorded product id stops a retry from creating a duplicate. Optionally, in publishShop re-read the item (items.byIdForShop) just before createProduct, skip it if !isPendingPublish(fresh), and build productFor from the fresh row, so a rename made before its turn reaches PayPal.

**Status:** fixed (`5a3de29`).

## S4. [setup, low] An item read with more than 10 prices can never be priced or fixed, and its edit drops every other edit saved in the same batch

`src/lib/catalog/edits.ts:72`

**Scenario:** normalize/buildVariants copies every prices[] entry into variants with no limit (normalize.ts:68-87, schemas.ts has no max). ItemUpdateSchema allows `variants: z.array(...).max(10)`. Take a price list with one item in 11+ sizes or lengths, say a tailoring or haircut list, or a pizza in many sizes, where one size is unreadable. That item gets a 'Needs a price' card, and every save from it (PriceCard, CheckCard 'Fix', a ReadyRow price edit) sends all 11 variants and is refused with 400 'updates.0.variants: Array must contain at most 10 element(s)'. The seller sees that technical text and can only remove the item. Because the save queue batches all pending item edits into one PATCH that applies all-or-nothing (applyItemUpdates), any other items' edits made within the same ~700 ms window are refused too. resync then reloads the server's menu, so those fixes disappear from the screen.

**Skeptic's evidence:** Throwaway vitest (now deleted): normalizeExtraction on an item with 11 labelled prices, one unreadable, gave 11 variants with ['MISSING_PRICE']. parseItemUpdates on a two-update batch (another item's rename, plus this item's 11 variants) threw 'updates.1.variants: Array must contain at most 10 element(s)' and refused the whole batch. The code: buildVariants copies every prices[] entry (src/lib/ai/normalize.ts:68-87), and the schema has no max (src/lib/ai/schemas.ts:22). ItemUpdateSchema has variants .max(10) (src/lib/catalog/edits.ts:72). Each fix action sends every variant: IssueCards.tsx:122, 160 and 207, and ItemLists.tsx:31 and 149. The save queue sends the batch in one PATCH (save-queue.ts:57, 67) and treats a 400 as refused and then resyncs (lines 102-105, 116-118). The other edits in that batch are lost, and the seller sees the technical zod message. It stays low: one item with 11 or more printed prices is rare.

**Fix:** Cap variants in normalize at the edit schema's limit. Export MAX_VARIANTS = 10 from src/lib/catalog/rules.ts, use it in edits.ts, and in buildVariants use it.prices.slice(0, MAX_VARIANTS). When prices were dropped, add CHECK with plain text such as 'Your menu lists more than 10 sizes; we kept the first 10.' Add a normalize test with 11 prices.

**Status:** fixed (`edd4723`).

## S5. [setup, low] A retake whose reading fails keeps the new photos on the server, but the retake screen goes back to the old photo count, so 'Add a page' duplicates pages or hits TOO_MANY_PHOTOS

`src/components/setup/ReadingStep.tsx:105`

**Scenario:** On the retake screen, a multipart POST /extract first saves the photos with setShopPhotos (setup.ts:65-76) and then reads them. If the reading fails (AI_ERROR when Claude is overloaded, TIMEOUT, or 429 BUSY from the readings limit), ReadingStep calls onUploadFailed(message), and SetupFlow shows the stale 'unreadable' RetakeStep with the old photoCount. The message says 'Your photos are saved, so you can try again', but the screen only offers Retake and Add a page, and no plain retry. Example: shop has 3 pages, the seller taps 'Add a page' with page 4, the server stores [p1,p2,p3,p4] and the reading fails. The screen still shows 3 pages, and tapping 'Add a page' again with the same photo is refused with 'Shelfie reads up to 4 photos at a time.' even though the strip shows 3. With 1-2 pages, the same retry silently stores the added page twice, and every later reading sends Claude a duplicated page and costs another paid image.

**Skeptic's evidence:** Code walk-through. In the multipart POST /extract, setShopPhotos stores the new photos (src/app/api/shops/[id]/extract/route.ts:48) before runReading (line 51). A reading failure then returns 502 READING_FAILED, or 429 RATE_LIMITED when allowLive refuses as BUSY (setup.ts:166 records a failed extraction). startReading turns either into {kind:'failed'} (src/components/setup/api.ts:37). ReadingStep.tsx:105 then calls onUploadFailed, and SetupFlow.tsx:19-22 only clears rerun and sets uploadError, so the stale 'unreadable' RetakeStep comes back with the old view.photoCount. That stale count drives canAdd and checkNewPhotos (RetakeStep.tsx:45, 55). On the server, setShopPhotos 'add' keeps shop.menuPhotoPaths, which already holds the uploaded page (setup.ts:66-68). Re-adding the same page therefore either stores it twice (a duplicate page sent to Claude on every later reading) or, at 3+1 pages, fails with TOO_MANY_PHOTOS even though the strip shows 3. The 'unreadable' view has no plain retry, while FailedStep does (RetakeStep.tsx:118-135). The page keys SetupFlow on `${readingId}:${view.step}` (src/app/shops/[id]/setup/page.tsx:51), so a refresh after a failed reading would remount into FailedStep with the right count. Low: it needs a reading failure right after an 'Add a page' upload, and a manual refresh recovers.

**Fix:** In SetupFlow.onUploadFailed, also call router.refresh() (useRouter from next/navigation). When the reading failed after the upload, the server's latest extraction is a new 'failed' row, so the page remounts into FailedStep ('Try again' re-reads the saved photos, with the right photo count). When the upload itself was refused (BAD_IMAGE, PHOTO_TOO_LARGE, TOO_MANY_PHOTOS, or the retakes 429), no extraction is created, the key is unchanged, and the local error stays on the RetakeStep.

**Status:** fixed (`b0ac869`).

## D1. [dashboard, low] The "Can't reach PayPal" banner never appears when PayPal is down, because every failed sync still stamps lastCheckedAt

`src/lib/seller/health.ts:20`

**Scenario:** paypalLooksUnreachable decides PayPal is unreachable when an open order between 2 min and 3 h old has a lastCheckedAt more than 2 min old ("the 15 s poller isn't getting through"), or when the order has a recent capture_error event. But syncOrder (src/lib/orders/service.ts:280-295) writes lastCheckedAt in a `finally` block, so the timestamp is updated even when deps.paypal.getOrder throws a network error or 5xx. Steps: an agent creates an order, the buyer approves on PayPal, then PayPal's API stops answering (sandbox outage or network loss). The poller runs every 15 s. Each getOrder fails, yet each pass sets lastCheckedAt to the current time. No capture is ever attempted, so no capture_error event is logged. I confirmed this with a throwaway Vitest (since deleted): fake PayPal, order approved, then 40 poller passes over 10 minutes with getOrder failing on each one ('fetch failed'). Result: status awaiting_approval, events ['created'], lastCheckedAt fresh, and paypalLooksUnreachable returned false. For the whole outage the dashboard shows the order as 'Waiting for approval: the buyer hasn't approved on PayPal yet' with no banner. The buyer has in fact approved. The banner promised in spec §4 ('Payments buyers make on PayPal will show up here as soon as it answers') never fires in the case it was written for. It only fires if the PayPal reads work and the capture alone fails, or if the poller isn't running at all.

**Skeptic's evidence:** I could not refute it, and I reproduced it. In src/lib/orders/service.ts:280-295, syncOrder wraps getOrder in a try/finally. Any error other than 404 (network TypeError or a PayPal 5xx) is rethrown as paypalUnavailable, and the `finally` at line 294 still writes lastCheckedAt = nowMs. That is intended: tests/orders/service.test.ts ('reports PAYPAL_UNAVAILABLE ... and still records the check') pins it, and src/lib/mcp/tools.ts:304 uses lastCheckedAt as the get_order_status throttle. The cost is that src/lib/seller/health.ts:20 ('nobody has checked lately') can never become true while the poller is running and PayPal fails fast. The only other trigger is a capture_error event (line 23), and no capture is attempted when getOrder fails. pollOnce (poller.ts:22-27) catches the error and moves on. The real routes use the same function: the dashboard page (src/app/shops/[id]/(dashboard)/page.tsx:32) and GET /api/shops/[id]/orders (route.ts:19) both call paypalLooksUnreachable. I ran a throwaway Vitest (tests/zz-verify-dashboard-1.test.ts, since deleted): create order, fake.approve, then 40 pollOnce passes 15 s apart with getOrder failing on each. Result with TypeError('fetch failed'): {status:'awaiting_approval', events:['created'], lastCheckedAgeMs:0, getOrderCalls:40, bannerAny:false}. A PayPalApiError(503) gave the same result. DECISIONS.md says nothing about the banner, and the earlier review (R1-R13 and the Refuted section) does not cover it. The banner does fire in one outage case: PayPal accepts the connection but never answers. Undici then holds the sequential poller for up to 300 s and the stamp is written with the old start time. So the finding holds for fast-fail outages (DNS, connection refused, 5xx), not for every outage. I lowered severity from medium to low. The banner is informational, no money or order state is lost, the order is captured on the first sync after PayPal recovers (well inside the 3 h poll window), and the only harm is that the seller misses a warning while the card says 'waiting for approval'.

**Fix:** Keep the lastCheckedAt write as it is (the get_order_status throttle at tools.ts:304 and the existing test depend on it). Add a process-wide marker on globalThis, the same pattern poller.ts uses so hot reloads don't duplicate it, for example `{ lastFailMs, lastOkMs }`. In syncOrder, set lastFailMs = nowMs in the getOrder catch when the error is not a 404 (right before `throw paypalUnavailable(...)`). Set lastOkMs = nowMs after getOrder returns, or on a 404. In paypalLooksUnreachable, also return true when `lastFailMs > (lastOkMs ?? 0) && nowMs - lastFailMs < RECENT_ERROR_MS` and some passed order is open. Add a test: approve an order, fail getOrder on several pollOnce passes, and expect the banner to be true. Then let one getOrder succeed and expect it to be false. Another option is a rate-limited 'sync_error' order event that health.ts treats like capture_error, but that event would also need handling in the order timeline in src/lib/seller/view.ts, so the in-memory marker is the smaller change.

**Status:** fixed (`42ab33b`).

## B1. [buyer, low] A reload during the reply after create_order loses the PayPal approval card for good

`src/components/shop/BuyerConsole.tsx:79`

**Scenario:** The reducer holds approval cards in `state.held` until the turn ends (console-state.ts:117-121), but the persist effect saves only `{ sessionId, entries }` (BuyerConsole.tsx:79), and restoreConsoleState starts with held = [] (console-state.ts:245-254). ## Refuted

- **L3** (lifecycle) The webhook event id is stored as processed before the order sync runs, so a restart or crash mid-sync turns PayPal's redelivery into a 'duplicate' 200 and the event is lost: The ordering is as described: recordWebhook commits an INSERT OR IGNORE (src/lib/db/repos/events.ts:22-27) at webhook/route.ts:75 before syncOrder at :88-89, and only a sync that throws calls forgetWebhook (:94). The headline trigger does not hold, though. On SIGTERM, which is what a Render deploy or restart sends, Next's start-server cleanup calls server.close() and waits for pending requests before process.exit(143) (node_modules/next/dist/server/lib/start-server.js:306-334, 364-365). An in-flight webhook sync of about one PayPal GET (plus a capture) therefore finishes inside Render's shutdown grace period, and its 200 or 503 reaches PayPal. Two paths remain. (a) A SIGKILL, OOM or crash lands inside the sub-second to few-second sync window, for an event about an order older than 3 h (the poller re-syncs newer orders, poller.ts:14-20), which in practice means a pending-capture completion days later. (b) A PayPal retry arrives while the first sync is still running. That needs PayPal to stall the sync past its own delivery timeout plus its retry delay, and the earlier review refuted the 'PayPal holds requests open' premise. Webhooks only run deployed with PAYPAL_WEBHOOK_ID set, and pending captures are rare in the sandbox. This is a theoretical atomicity gap, not a demonstrated failure.

- **C2** (consistency) A re-approval that comes back within 5 s of a decline is dropped by the return-URL throttle; the receipt keeps saying 'declined' and the order later expires even though PayPal holds a new approval: The code facts are right. syncOrderShared sets lastThrottledSync when a sync starts (service.ts:333-341), and a throttled call returns the stored order. After a decline, only return_url or webhook triggers a capture (service.ts:401-405). The scenario is not reachable by a person, though. The window is 5 s from the start of the first return_url sync, and that sync itself includes PayPal getOrder plus the declined capture round trip before the 303. In what is left of the 5 s, the buyer would have to load /o/[ref], read it, click 'Try PayPal again', load PayPal's page, choose another funding source and approve, and be redirected back. On the verified path that means typing a full guest card form (card, expiry, CVV, address). That takes far more than 5 s. The tool description (tools.ts:75), the server instructions (instructions.ts:20) and the IDEMPOTENCY_CONFLICT hint all say the key is for retrying the same request, and next_step says plainly that the order 'already exists with status cancelled'. - **C5** (consistency) get_order_status is advertised as read-only, but it captures the payment and writes the order: The spec chooses this on purpose: docs/superpowers/specs/2026-11-06-shelfie-design.md:205 lists '`get_order_status` (readOnly)' and also says '— syncs with PayPal first'. The only write it can cause is completing a capture the human already approved on PayPal (approveAndCapture). Auto-running it or calling it speculatively therefore causes no harm the user didn't approve. The scenario names no concrete wrong outcome. - **C7** (consistency) The receipt always says the approval link 'works for 60 minutes', however much of the window is left: The scenario's entry points don't exist.
