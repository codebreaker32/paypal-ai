# Whole-codebase correctness review (session 5, 2026-11-06)

A workflow of 4 area reviewers (orders, PayPal client, agent door, setup), each followed by a skeptic that tried to refute every finding by reading the code and, where useful, running a throwaway test. 13 findings were confirmed and 3 refuted. Each entry below gives the reviewer's failure scenario and suggested fix, then the skeptic's evidence and corrected fix.

## R1. [paypal, medium] Agent Toolkit instance keeps PayPal's shared OAuth token past its expiry, so Add tracking (and the brief's get_order) fail with 401 for up to 30 minutes

`src/lib/paypal/toolkit.ts:119`

**Scenario:** The wrapper assumes that rebuilding the toolkit every 30 minutes gives it a fresh token. PayPal returns the same access token to every client_credentials grant until that token expires, with expires_in counting down. I checked this against the sandbox with these credentials: two grants a few seconds apart gave the same token hash with expires_in 30691 and then 30687, and api.sandbox.paypal.com and api-m.sandbox.paypal.com hand out the same token. Toolkit 1.11.0 caches the token forever (`this._accessToken = this._accessToken || await getAccessToken()`). Example: the shared token expires at 14:00. A paid order at 13:50 runs the brief, which builds sharedInstance and gets the token with 10 minutes left. At 14:05 the seller presses Add tracking. The toolkit's get_order returns 401 (invalid_token), and parseResult turns it into a ToolkitError, so the seller gets a 502 PAYPAL_REJECTED reading 'PayPal said: Access Token not found in cache' (or similar). Every retry fails the same way until builtAt+30min (14:20). The brief agent's get_order and get_shipment_tracking also fail in that window. This repeats each time the roughly 9-hour token rolls over, whenever the instance was built in that token's last 30 minutes. No 401 path drops sharedInstance.

**Suggested fix:** In `call()`, when parseResult throws a ToolkitError with status 401, set sharedInstance (or localInstance) to null and retry once with a freshly built instance. That rebuilt instance fetches the new token, because PayPal only issues one after the old one expires. Another option is to build the toolkit from a token whose expiry the REST client already tracks.

**Verifier evidence:** Toolkit 1.11.0 (node_modules/@paypal/agent-toolkit/ai-sdk/index.js): PayPalAgentToolkit builds a single client `new F({clientId, clientSecret, context})` per instance, and `getHeaders()` does `this._accessToken=this._accessToken||await this.getAccessToken()`, so the token is cached for the life of the instance. Its error handler `h()` turns a PayPal 401 into an LlmError {ok:false,status:401}, with no refresh. In the wrapper, src/lib/paypal/toolkit.ts:118-121 rebuilds the instance only when `now()-builtAt >= TTL_MS` (30 min), and `call()` (line 126) has no 401 path. Sandbox check with the repo's .env (token hashed, never printed): two client_credentials grants 3 s apart returned the same token hash 0c4c16a390c6 with expires_in 29880 and then 29877. That matches the finder's 30691 from about 13 min earlier, so PayPal keeps handing out the same token until it expires. A rebuilt instance therefore gets whatever life the shared token has left, not a fresh 9 h. Throwaway test tests/zz-verify-paypal-1.test.ts (now deleted) used an injected factory: an instance built 10 min before the token expires returns ToolkitError(401) at minutes 15, 16, 20, 25 and 29, with factory builds == 1 (no rebuild on 401), and works again only at minute 30. It passed. With steady traffic the instance is rebuilt every 30 min, so one build lands in the last 30 min of every ~9 h token. That gives roughly 15 min of failures on average at each rollover: Add tracking returns 502 PAYPAL_REJECTED from actions.ts:141, and the brief agent's get_order and get_shipment_tracking tool calls error. DECISIONS.md has no entry covering this.

**Verifier's fix:** In createSellerToolkit's `call()`, catch a ToolkitError whose status is 401. Drop the cached instance (`sharedInstance = null`, or `localInstance = null` for injected factories) and retry the call once on a freshly built instance. The old token has expired by then, so the new instance's grant gets a new token. A 401 is rejected before PayPal processes the request, so retrying create_shipment_tracking cannot create a duplicate tracker.

**Status:** fixed (`89a4e41`): a 401 drops the cached toolkit and retries once on a fresh one. Verified against the real sandbox: a toolkit holding a bogus token got PayPal's real 401, was rebuilt and the call succeeded; without the fix the same test fails with that 401.

## R2. [paypal, low] The unauthenticated webhook route buffers the whole request body before any signature or size check

`src/app/api/paypal/webhook/route.ts:32`

**Scenario:** POST /api/paypal/webhook starts with `await req.text()`, before the 'cheap guard' for signature headers. The app has no proxy or middleware, and Next route handlers have no default body limit. Anyone can stream a multi-GB or endless chunked body to this public endpoint, with or without PAYPAL_WEBHOOK_ID set. The single Node process buffers it into one string until it hits V8 string limits or runs out of memory. That takes down the server that also runs the payment poller and the agent door. Real PayPal events are a few KB.

**Suggested fix:** Check the PayPal signature headers before reading the body. Reject requests whose Content-Length is missing or over a small cap (for example 64 KB) with 413, or read the stream with a byte limit, before calling req.text().

**Verifier evidence:** src/app/api/paypal/webhook/route.ts:32 runs `const raw = await req.text()` as its first statement, before the signature-header check (lines 38-40) and before the production 503 for an unset PAYPAL_WEBHOOK_ID. The repo has no middleware.ts or proxy.ts, and next.config.ts sets no body limit. Per node_modules/next/dist/docs/.../proxyClientMaxBodySize.md, Next's only default body cap (10 MB) applies when a proxy is used, so route handlers read bodies with no limit. The codebase caps other public inputs on purpose: the MCP door passes `maxRequestBodySize: MAX_MCP_BODY_BYTES` (src/lib/mcp/server.ts:43), and uploads check Content-Length (src/lib/uploads.ts:66-77). The webhook has no cap. Throwaway test tests/zz-verify-paypal-4.test.ts (now deleted) set PAYPAL_WEBHOOK_ID, sent an unsigned 64 MB streamed body with no signature headers and called the real POST handler. All 64 of 64 MB chunks were pulled from the stream before the route returned 400 BAD_SIGNATURE. Anyone can therefore make the single Node process, which also runs the payment poller and the agent door, buffer arbitrarily large bodies, limited only by Node's 300 s requestTimeout. Concurrent large posts can exhaust memory on a small instance. /api/assistant/[slug] has the same unbounded `req.json()`, so a shared bounded reader would cover both.

**Verifier's fix:** Before reading the body, reject a request whose Content-Length is missing or over a small cap (64 KB is generous for PayPal events) with 413 or 411. When PAYPAL_WEBHOOK_ID is set, also run the signature-header check first. Then read the body through a byte-limited stream reader that stops and returns 413 once the cap is exceeded, rather than `req.text()`. Reuse the same helper for /api/assistant/[slug].

**Status:** open

## R3. [orders, medium] A refused capture leaves the order stuck in 'approved' for good, and the seller is told the payment will land in seconds

`src/lib/orders/service.ts:286`

**Scenario:** The buyer approves, and our capture gets a non-transient 4xx such as 422 TRANSACTION_REFUSED, PAYER_CANNOT_PAY or 403. Lines 283-288 release the claim, log capture_failed and leave the order 'approved'. From then on nothing can move it. The poller and MCP skip it (line 234, lastCaptureFailure). reconcile's VOIDED branch (lines 211-214) only cancels 'awaiting_approval' orders, so PayPal voiding the order later is ignored. expireIfDue only handles 'awaiting_approval'. cancelOrder throws InvalidTransition and the error is swallowed. After 3 h the poller stops looking at the order. I reproduced this with a throwaway test (deleted afterwards): TRANSACTION_REFUSED, then PayPal VOIDED, then cancel URL, then the poller at +2 h and +7 h. The order was still 'approved' and still in groupOrders().waiting. The buyer's receipt and the agent both say PayPal refused and nothing was charged. The seller dashboard has no captureRefused handling: it shows 'Approved, taking payment' and the detail page says 'The payment should land in a few seconds' (orders/[orderId]/page.tsx:95). The order stays in the 'Not paid yet' total forever.

**Suggested fix:** Make the refused-capture state terminal or visible. Either move it to 'failed' after the buyer's last retry window (for example at expiresAt, or on VOIDED or 404 from PayPal for an 'approved' order with lastCaptureFailure), or allow 'approved' + 'expired'/'cancelled' when lastCaptureFailure is set. Also show lastCaptureFailure() on the seller dashboard and order detail ('PayPal refused the payment; nothing was charged') instead of 'should land in a few seconds'.

**Verifier evidence:** Code path: src/lib/orders/service.ts:283-288 handles any non-transient capture 4xx by releasing the claim, logging capture_failed and leaving the order 'approved'. Guards and exits that never move it: line 234 skips poller/mcp while lastCaptureFailure() is set. Lines 211-214 handle VOIDED only for 'awaiting_approval'. Line 216: a 404 or any other status goes to expireIfDue, which (line 221) only acts on 'awaiting_approval'. state.ts:26-33 has no cancelled/expired transition out of 'approved', so cancelOrder (service.ts:390-395) catches InvalidTransition and only logs an ignored event. poller.ts:12-13 keeps polling 'approved' orders only while createdAt is within 3 h. countOpen (repos/orders.ts:90) counts only awaiting_approval, so the shop's capacity is NOT blocked.

Throwaway test tests/zz-verify-orders-1.test.ts (since deleted) did: approve, then return_url capture fails with 422 TRANSACTION_REFUSED, then the fake order is set to VOIDED, then poll and webhook sync, then cancelOrder, then poll at +2 h and +7 h, then return_url with VOIDED, then return_url with 404. Output: `FINAL approved refused? true waiting? 1`, `TIMELINE ["Order created by an AI assistant","Approved on PayPal"]`, `EVENTS [created, paypal_approved, capture_failed, cancelled(cancel_url, ignored)]`.

Seller side: timelineEntries (src/lib/seller/view.ts:71-110) has no capture_failed case, so the refusal is invisible. orderStatusMeta (src/components/dashboard/status.tsx:27) shows 'Approved, taking payment'. The detail page (src/app/shops/[id]/orders/[orderId]/page.tsx:95) says 'The payment should land in a few seconds.' groupOrders keeps it in 'waiting', in the 'Not paid yet' total. The detail page's AutoRefresh stays active.

Buyer side: the receipt (src/app/o/[ref]/receipt-status.ts:58-64) and the MCP status both say PayPal refused and nothing was charged. So buyer and seller see contradictory states, permanently. The existing test tests/orders/service.test.ts:369 only covers 'stays approved so the buyer can retry'; it does not cover a terminal state. No DECISIONS.md entry covers this. Severity medium is fair: no money is lost, but the user-visible state is wrong forever and the order never settles.

**Verifier's fix:** Give the refused state an exit and show it to the seller. (1) In reconcile, treat VOIDED, or a 404/NOT_FOUND, on an 'approved' order with lastCaptureFailure() as terminal: add an approved -> failed (or approved -> expired) transition, e.g. a 'capture_refused_final' event, and also apply it once nowMs passes expiresAt. Extend the poller filter so 'approved' orders with a capture_failed past their window are still swept. (2) In the order detail ActionCard and orderStatusMeta, check lastCaptureFailure (pass a captureRefused flag as the receipt does) and show 'PayPal refused the payment; nothing was charged. Don't hand over or ship.' instead of 'should land in a few seconds'. Add a capture_failed case to timelineEntries.

**Status:** fixed (`d354161`, `24f8e11`): the seller sees "PayPal refused payment" (nothing charged, don't hand over or ship) and a `capture_failed`/`capture_refused` timeline entry; a refused order becomes `failed` on VOIDED, 404 or once its window passes, and the poller sweeps it after 3 h.

## R4. [orders, low] One buyer approval can trigger repeated capture attempts on a declined card: the return URL and webhook skip the decline/refusal guards, and the return URL is not throttled

`src/lib/orders/service.ts:229`

**Scenario:** Deployed with the README's CHECKOUT.ORDER.APPROVED webhook. The buyer approves with a card that gets declined. The return URL (redirect is immediate) captures with cap-<id>, gets 422 INSTRUMENT_DECLINED, and the order goes back to awaiting_approval. A few seconds later the webhook for that same approval arrives. syncOrder(..., 'webhook') sees PayPal still APPROVED, and the guard at line 229 only applies to poller/mcp, so it runs paypal_approved, claims and captures again with cap-<id>-1 on the same declined instrument. That is a second decline on the buyer's card for one approval, and the receipt flips from 'Confirming' back to 'declined'. Also, GET /api/paypal/return?o=<ref> has no throttle or rate limit, and after a decline or capture_failed every hit bypasses the guards. Each reload, link-preview fetch, or request from anyone holding the ref fires a fresh capture call (the request-id suffix keeps increasing) plus a GET against the single shared merchant credentials. In the plain awaiting state each hit still costs a PayPal GET. Anyone can create their own order through the open MCP door, so anyone can hold a ref.

**Suggested fix:** Only bypass the post-decline/post-refusal guard when there is evidence of a new approval. For example, skip the webhook-triggered capture when the event's create_time is older than the last capture_declined/capture_failed event, and apply the same lastCheckedAt throttle as get_order_status (5 s) or a per-IP limit to /api/paypal/return so repeated hits cannot drive repeated capture calls.

**Verifier evidence:** Real, but low impact and narrower than the title suggests. Guard at src/lib/orders/service.ts:229 (and 234) applies only to source 'poller' and 'mcp'. The webhook (src/app/api/paypal/webhook/route.ts:76 calls syncOrder(...,'webhook')) and the return URL (src/app/api/paypal/return/route.ts:13) bypass it. The comment at 230-231 says PayPal still reports APPROVED after a decline. The request-id suffix at 252-253 increases each time, so every bypassing sync is a fresh capture attempt at PayPal.

Throwaway test tests/zz-verify-orders-2.test.ts (since deleted) did: approve with nextCapture=DECLINED_422, then syncOrder 'return_url', which went to awaiting_approval; then syncOrder 'webhook' for the same approval. Output: `CAPS after return+webhook ["cap-FAKE0000000000001","cap-FAKE0000000000001-1"]`. Five more return_url hits gave seven capture calls (suffixes -2 to -6). Poller and mcp calls added none.

The return route has no rate limit or lastCheckedAt throttle. Only create_order is rate-limited (src/lib/mcp/tools.ts:185,273), and get_order_status has the 5 s throttle (DECISIONS.md:36).

Limits on impact: no money is moved twice. PayPal cannot capture one order twice (ORDER_ALREADY_CAPTURED is handled at 258-265), and the final state is still correctly 'declined'. If the webhook arrives while the first capture still holds the claim, claimCapture (repos/orders.ts:128-138) makes it a no-op, so the duplicate happens only when the webhook lands after the decline. Order refs are 16-char random ids (src/lib/domain/ids.ts), so repeated return-URL hits can only come from the holder of that order's ref, against their own order. The concrete harm is (a) one redundant capture attempt on a known-declined instrument per declined approval once the webhook is configured, and (b) an unthrottled public endpoint. Each hit costs a PayPal GET, plus a capture after a decline or refusal, on the single shared merchant credential (a quota-burn and DoS vector). No DECISIONS.md entry covers it.

**Verifier's fix:** Throttle /api/paypal/return per order: skip the PayPal sync when lastCheckedAt is under about 5 s old, as get_order_status does, and/or add a per-IP allow() bucket. For the webhook, bypass the post-decline/post-refusal guard only for a CHECKOUT.ORDER.APPROVED event whose create_time is later than the last capture_declined/capture_failed event row. Pass the event time into syncOrder, or record the decline time and compare it there. Otherwise treat the webhook like the poller.

**Status:** fixed (`5fd5523`): return-URL syncs are throttled to one per 5 s per order; a webhook approval no newer than the last declined or failed capture doesn't capture again.

## R5. [orders, low] The webhook buffers an unbounded request body before its cheap unsigned-request check

`src/app/api/paypal/webhook/route.ts:32`

**Scenario:** POST /api/paypal/webhook is public. Line 32 runs `await req.text()` on the whole body before the signature-header guard at line 39, which exists to make unsigned POSTs cheap. Production with no PAYPAL_WEBHOOK_ID (it then returns 503) also reads the body first. There is no proxy, so Next sets no body limit for route handlers. An unauthenticated client can send a multi-hundred-MB chunked body with no PayPal headers, and the server buffers all of it into one string before answering 400. A few concurrent requests exhaust memory on a small Render instance and take down checkout, the return URL and the poller for every shop.

**Suggested fix:** Check the PayPal transmission headers (and the webhook-ID configuration) before reading the body. Reject a Content-Length over a small cap (PayPal events are a few KB; for example 64 KB), and read the stream with a byte limit so chunked bodies are also capped.

**Verifier evidence:** src/app/api/paypal/webhook/route.ts:32 runs `const raw = await req.text();` before the webhook-ID check (line 34), the production 503 (line 49-50) and the signature-header guard (lines 38-40). There is no middleware.ts or proxy.ts, and next.config.ts sets no limit. Per node_modules/next/dist/docs/.../proxyClientMaxBodySize.md, the 10 MB buffer cap applies only when a proxy is used, so route handlers get the raw stream with no limit.

Throwaway test tests/zz-verify-orders-3.test.ts (since deleted) did: PAYPAL_WEBHOOK_ID stubbed, then POST with no PayPal headers and a 200 x 1 MB streamed body (duplex 'half'). Output: `status=400 chunksPulled=200/200 rssBeforeMB=77 peakMB=296`. The whole 200 MB was pulled and held in memory (+~220 MB RSS) before the cheap 400. Concurrent requests multiply this, and a body over V8's max string length makes text() throw after buffering anyway.

The codebase caps body size elsewhere on purpose: src/lib/mcp/server.ts:14,43 sets MAX_MCP_BODY_BYTES = 64 KB for the agent door, and src/lib/uploads.ts:68-78 refuses an oversized or missing Content-Length before reading. So the webhook is an uncapped exception on a public, unauthenticated endpoint. Note that /api/assistant/[slug] (req.json()) has the same pattern, outside this area. No DECISIONS.md entry covers it.

**Verifier's fix:** Before reading the body: (1) return 503 early if no webhook ID is set in production, and check the five paypal-transmission-* headers first. (2) Reject Content-Length above a small cap (e.g. 64 KB) with 413. (3) Read req.body through a byte-limited reader that aborts and answers 413 once the cap is exceeded, so chunked bodies without Content-Length are also bounded. Then pass the collected string to verifyWebhookSignature and JSON.parse.

**Status:** open

## R6. [door, high] client_request_id is matched per shop only, and request content is never compared, so one buyer gets (and can pay for) another buyer's order

`src/lib/orders/service.ts:86`

**Scenario:** createOrderForShop looks up byClientRequestId(shop.id, key) and returns the stored order without comparing items, options, quantities or fulfillment. Outside MCP agents' keys are not scoped. The console scopes its keys by session, and buyer-console.ts says this is because models invent readable keys that two buyers can both produce. Reproduced with two MCP clients on different IPs. Alice sends create_order {Almond croissant x2, pickup, client_request_id:'order-1'}. Bob sends {Sourdough loaf x5, shipping, client_request_id:'order-1'}. Bob gets back Alice's order_ref, lines, $9.50 total and approval_url, with status awaiting_approval and next_step 'Give the user approval_url'. If Bob approves, he pays for Alice's croissants and Alice's order shows as paid. Bob's loaves are never ordered. If Alice's order is already paid, Bob's agent gets status 'paid' for an order Bob never placed. Anyone can also try common keys ('order-1', 'test') to collect other buyers' order_ref and approval_url, then call get_order_status to read their tracking numbers. Within one console conversation, a model that reuses its key for a changed order gets the old order back.

**Suggested fix:** Store a fingerprint of the normalized request (item_id, option_id, quantity per line, plus fulfillment) with the key. On a key hit with a different fingerprint, return a named error (e.g. INVALID_ARGUMENTS 'client_request_id was already used for a different order') instead of the stored order. Also scope outside agents' keys to the caller, e.g. hash(rate identity + key), the way the console already scopes keys by session.

**Verifier evidence:** Code path: src/lib/mcp/tools.ts:282 passes args.client_request_id through unchanged for outside agents. src/lib/orders/service.ts:84-87 returns ordersRepo.byClientRequestId(db, shop.id, key) as soon as it exists, with no check of lines, options, quantities or fulfillment. src/lib/db/repos/orders.ts:70-72 looks up by (shop_id, client_request_id) only, and schema.sql:93 has UNIQUE(shop_id, client_request_id). Only the console scopes its keys (src/lib/agent/buyer-console.ts:270-280), and its comment names this exact collision risk. Nothing in DECISIONS.md covers it. Proof (throwaway tests/zz-verify-door-1.test.ts, deleted, passed): two POSTs to the real route handler (src/app/s/[slug]/mcp/route.ts) from X-Forwarded-For 198.51.100.1 (Alice: Almond croissant x2, pickup, key 'order-1') and 203.0.113.7 (Bob: Sourdough loaf x5, shipping, key 'order-1'). Bob's result had isError falsy, the same order_ref and approval_url as Alice's, lines[0].name 'Almond croissant' and status 'awaiting_approval'. The fake PayPal recorded exactly 1 createOrder, so Bob's order was never placed. Extra impact the reviewer missed: GET /api/paypal/cancel?o=<order_ref> (src/app/api/paypal/cancel/route.ts) has no auth. With the harvested ref, Bob cancelled Alice's order in the same test, and its status became 'cancelled'. Harvested refs also open the public receipt /o/<ref> and get_order_status (tracking).

**Verifier's fix:** In createOrderForShop, store a fingerprint with the key: a sha256 of the normalized lines (sorted item_id/option_id/quantity) plus the resolved fulfillment, in a new orders.request_hash column. On a key hit whose fingerprint differs, throw OrderError('INVALID_ARGUMENTS', 'client_request_id was already used for a different order', ...) and do not return the stored order. Do the same check for an in-flight promise hit by keeping the fingerprint next to the promise. Also scope outside agents' keys to the caller before the lookup, e.g. key = hash(rateIdentity + '\n' + client_request_id), as the console does with its session. The cancel URL also lets anyone who knows a ref cancel that order. Consider requiring PayPal's token query param to match order.paypalOrderId there.

**Status:** fixed (`aba4602`): a matched `client_request_id` returns the stored order only when items, options, quantities and fulfillment match; otherwise `IDEMPOTENCY_CONFLICT`. True retries stay idempotent.

## R7. [door, medium] One anonymous caller can fill the shop-wide 10-unpaid-order cap and block every other buyer for an hour; the cap is not atomic either

`src/lib/orders/service.ts:100`

**Scenario:** MAX_OPEN_ORDERS_PER_SHOP is counted per shop (countOpen counts awaiting_approval rows). The only per-caller limit is CREATE_ORDER_RATE, which allows 30 calls per IP per hour. A single IP with no auth, using any MCP client or the shop's own buyer console, sends 10 create_order calls. Each one also creates a real PayPal order. Every other buyer and agent then gets TOO_MANY_OPEN_ORDERS for 60 minutes, and the attacker can repeat this every hour. The check is also check-then-act: countOpen runs before the PayPal createOrder await and the row is inserted after it, so concurrent calls all see the old count. Verified: 25 concurrent create_order calls from one client all succeeded (cap of 10 bypassed), and a second buyer on another IP was then refused with TOO_MANY_OPEN_ORDERS. Not covered by docs/DECISIONS.md.

**Suggested fix:** Add a per-caller cap on unpaid orders, e.g. at most 2-3 awaiting_approval orders per rate identity (IP or console:<buyer ip>) per shop, checked before the shop-wide cap. Reserve the slot synchronously before the PayPal await, either with an in-process counter keyed by shop or by inserting a pending row, so concurrent calls can't pass together. Consider lowering CREATE_ORDER_RATE as well.

**Verifier evidence:** Code path: src/lib/orders/service.ts:31,100 checks ordersRepo.countOpen(db, shop.id), which counts awaiting_approval rows per shop (src/lib/db/repos/orders.ts:90-92). The only per-caller limit is CREATE_ORDER_RATE, 30/hour per IP (src/lib/mcp/tools.ts:25,185). The count runs before `await deps.paypal.createOrder` (service.ts:116), and the row is inserted only afterwards (service.ts:136), so the check-then-act spans an await. The seller has no way to cancel unpaid orders: cancelOrder is only reachable through the PayPal cancel URL, so attacker orders block the shop until they expire after 60 minutes. Spec section 10 sets '> 10 unpaid per shop' and section 15 lists the open-order limit as an anti-spam measure. Neither the spec nor DECISIONS.md addresses one caller using up the cap. Proof (throwaway tests/zz-verify-door-2.test.ts, deleted, both tests passed): (a) 10 sequential create_order POSTs from 198.51.100.66 all succeeded, then a call from 203.0.113.200 got isError with TOO_MANY_OPEN_ORDERS. (b) 25 concurrent create_order POSTs to another shop from one IP all succeeded: countOpen reached 25 and the fake PayPal recorded 25 createOrder calls, so the cap of 10 was bypassed. The fake PayPal answers almost instantly, and real PayPal latency (hundreds of ms) widens the window.

**Verifier's fix:** Add a per-caller cap before the shop-wide one, e.g. at most 3 awaiting_approval orders per (shop, rate identity). This needs the rate identity on the order: either a hashed caller column on orders (passed from ShopServerDeps.clientIp through CreateOrderInput), or an in-memory map like the rate limiter. Reserve the slot synchronously before the PayPal await. The app is one process with an in-memory rate limiter, so a per-shop in-process counter works: increment it with the countOpen check, decrement it in finally after the insert. Alternatively insert the row first as a pending reservation. Lowering CREATE_ORDER_RATE (e.g. to 10/hour) also helps.

**Status:** fixed (`2181b6c`, `381eb32`): a per-caller cap of 3 unpaid orders per shop (keyed on the door's rate identity, stored hashed in `orders.client_key`, added to existing databases), the shop-wide cap of 10 kept, both checked inside the insert's transaction.

## R8. [door, low] The 5-second get_order_status sync throttle can be bypassed with concurrent calls, so one order_ref can drive unlimited PayPal GETs on the shared credentials

`src/lib/mcp/tools.ts:304`

**Scenario:** get_order_status reads order.lastCheckedAt and calls syncOrder. lastCheckedAt is written only in syncOrder's finally (service.ts:200), after PayPal answers, so every call that starts before the first one finishes still sees the old timestamp. get_order_status has no rate limit, and the stateless SDK transport accepts JSON-RPC batches of up to 100 requests in one 64 KB POST, which it runs concurrently. Verified: 50 concurrent get_order_status calls for one order made 50 PayPal getOrder calls. An attacker creates one order of their own (it stays open for 60 minutes) and repeatedly POSTs batches of 100 status calls, about 100 PayPal requests per HTTP request. This can get the single platform merchant's credentials rate-limited (429), and then create_order and captures fail for every shop.

**Suggested fix:** Remove the gap between the check and the write. Either keep an in-process map of syncOrder promises per order id (like createOrderForShop's inflight map) and let concurrent callers share one sync, or atomically claim the sync window before the await (UPDATE ... SET last_checked_at = now WHERE id=? AND (last_checked_at IS NULL OR last_checked_at < now-5s)). Also add a per-IP rate limit to get_order_status.

**Verifier evidence:** Code path: src/lib/mcp/tools.ts:303-304 reads order.lastCheckedAt and calls syncOrder. src/lib/orders/service.ts:199-200 writes lastCheckedAt only in the finally, after `await deps.paypal.getOrder` (service.ts:192). get_order_status has no rateLimit; only create_order sets one, at tools.ts:273. In @modelcontextprotocol/sdk, server/webStandardStreamableHttp.js:504-512 accepts JSON-RPC arrays up to MAX_BATCH_SIZE = 100 (server/requestBody.js:4). In JSON-response mode (lines 594-606) it dispatches onmessage for every message without awaiting, so the handlers run concurrently. Proof (throwaway tests/zz-verify-door-3.test.ts, deleted, passed): created one order, then sent one 13,411-byte POST (well under the 64 KB cap) holding 100 get_order_status calls for that order_ref, with fake getOrder delayed 50 ms.
