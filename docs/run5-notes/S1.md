# S1 notes (delete and password API)

The server side came first; the screens and copy followed in a second session (see "Screens and copy" below).

## Routes added

| Route | Body | Success | Refusals |
|---|---|---|---|
| `DELETE /api/shops/[id]` | `confirmName`, `currentPassword` | 204 | 403 `DEMO_SHOP`, 403 `ACCOUNT_REQUIRED`, 400 `NAME_MISMATCH`, 403 `PASSWORD_REQUIRED` / `PASSWORD_WRONG`, 404, 409 `OPEN_ORDERS`, 429, 503 `BUSY` |
| `POST /api/account/password` | `currentPassword`, `password` | 204 | 401, 400 `WEAK_PASSWORD`, 403 `PASSWORD_REQUIRED` / `PASSWORD_WRONG`, 429, 503 `BUSY` |
| `DELETE /api/account/sessions` | none | 204 | 401 |
| `DELETE /api/account` | `currentPassword` | 204, cookie cleared | 401, 403 `PASSWORD_REQUIRED` / `PASSWORD_WRONG`, 409 `OPEN_ORDERS` naming shops, 429, 503 `BUSY` |

The client can show `error.message` as it stands for `OPEN_ORDERS`: the shop route uses the brief's sentence, with a singular form for one order. The account route names each blocked shop with its count.

## Deviations and choices

- **No `addMissingColumns` entry.** `retired_slugs` is a new table, and `schema.sql` runs with `CREATE TABLE IF NOT EXISTS` on every open, so older databases get it from there. `addMissingColumns` is only for columns on existing tables.
- **An unattached shop has no password to check.** With `SHELFIE_ALLOW_GUEST_SHOPS` on (harnesses only), `DELETE /api/shops/[id]` needs `confirmName` and the owner cookie, and ignores `currentPassword`. With guests off it is 403 `ACCOUNT_REQUIRED`.
- **`confirmName` is trimmed and case-sensitive.**
- **The brief named no status for a successful shop delete.** It returns 204, matching `DELETE /api/account`.
- **New error codes the brief did not name:** `NAME_MISMATCH` (400) and `DEMO_SHOP` (403).
- **`DELETE /api/account/sessions` takes no password.** The brief gives it no `currentPassword`, and it can only log out devices.

## Behaviour worth knowing

- The open-order check, session check and password compare-and-set all run inside the delete transaction, so a request that waited on a hash answers for what is true at commit.
- Files are removed after the commit and best effort: a failure leaves a stale file, never a half-deleted shop.
- Products already published to the PayPal sandbox catalog are not removed; the delete covers Shelfie's rows and files, as the brief's copy says.

## Deviations and choices

- **The delete sheet shows only for account-owned shops that are not the demo shop.** The demo is refused by the route, and an unattached shop has no password to confirm with. Unattached shops (harness only) can still use the API.
- **Copy uses a typographic apostrophe** (`can’t`, `shop’s`), matching every other string in the app, where the brief has straight ones.
- **`Delete account` is an inline form, not a sheet.** The brief gives the sheet only to Delete shop, and typing the password is the confirmation.
- **The sheet also has a `Cancel` button**, which the brief didn't list, so the danger button isn't the only labelled way out on a phone.
- **`useAuthForm` gained `finish()`**, because it stayed busy after success (every earlier form navigates away), and Change password stays on the page.
- **`Sheet`'s title now wraps long words** (`[overflow-wrap:anywhere]`), for a long shop name in `Delete {name}?`.
- **Deleting your only shop lands on `/shops/new`**: `/shops` redirects an account with no shops there. The spec keeps a second shop so the list can be checked.
